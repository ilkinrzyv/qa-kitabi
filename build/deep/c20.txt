### Git və GitHub fərqi
Git kompüterində işləyən proqramdır — internet olmadan da commit etmək olar. GitHub (eləcə də GitLab, Bitbucket) repo-ların uzaq nüsxəsini saxlayır və üzərinə komanda alətləri əlavə edir: pull request, code review, issue-lar, Actions (CI).

### Commit nədən ibarətdir?
Hər commit-in unikal identifikatoru (hash, məsələn, `a1b2c3d`), müəllifi, tarixi, mesajı və əvvəlki commit-ə istinadı var. Bu zəncir layihənin tam tarixçəsidir: “bu sətri kim, nə vaxt və niyə dəyişib?” sualının cavabı oradadır.

### Conflict necə görünür?
```text
<<<<<<< HEAD
await expect(badge).toHaveText('1');
=======
await expect(badge).toHaveText('2');
>>>>>>> feature/two-products
```
`<<<<<<<` ilə `=======` arası sənin cari budağının versiyası, `=======` ilə `>>>>>>>` arası isə birləşdirilən budağın versiyasıdır. Düzgün variantı saxla, işarələri sil, sonra `git add` və `git commit` et. Conflict qorxulu deyil — Git sadəcə “hansını saxlayım?” deyə soruşur.

### Tipik yanlış anlama
“Git yalnız proqramçılar üçündür.” Avtomatlaşdırma kodu, Markdown formatında test sənədləri, hətta test datası da Git-də saxlanır. Tester üçün Git komanda ilə eyni “dildə” işləmək deməkdir.

### Səhvləri geri qaytarmaq
| Vəziyyət | Əmr |
| --- | --- |
| Fayldakı commit olunmamış dəyişikliyi ləğv et | `git restore fayl.js` |
| Səhvən staging-ə əlavə etdiyin faylı çıxar | `git restore --staged fayl.js` |
| Son commit-in mesajını düzəlt (hələ push olunmayıb) | `git commit --amend -m "Yeni mesaj"` |
| Push olunmuş commit-i ləğv et | `git revert <hash>` — ləğvedici yeni commit yaradır |
Push olunmuş tarixçəni yenidən yazmaq (məsələn, `git reset --hard` və `git push --force`) komanda yoldaşlarının işini poza bilər — komandanın razılığı olmadan etmə.

### Müvəqqəti saxlama: stash
`git stash` yarımçıq dəyişiklikləri kənara qoyur ki, başqa budağa keçə biləsən; `git stash pop` onları geri qaytarır. Yarımçıq iş zamanı təcili baq yoxlamasına keçəndə çox rahatdır.

### Tarixçəni araşdırmaq
- `git log --oneline --graph` — budaqlarla birlikdə qısa tarixçə.
- `git show a1b2c3d` — bir commit-in tam dəyişikliyi.
- `git blame tests/cart.spec.js` — hər sətri kim və hansı commit-də dəyişib.

“`git add .` həmişə təhlükəsizdir.” Bu əmr bütün dəyişiklikləri əlavə edir — təsadüfi fayllar, loqlar, hətta şifrə faylı da commit-ə düşə bilər. Əvvəl `git status`, sonra lazım olan faylları adları ilə əlavə et.

@addımlar

2. **Fərqi yoxla:** `git diff tests/login.spec.js` — həm düzəliş, həm də `console.log` sətri görünür.

### git bisect — defektin “doğum günü”
Test dünən keçirdi, bu gün düşür, arada 64 commit var. Hamısını bir-bir yoxlamaq əvəzinə Git ikili axtarış edir: ortadakı commit-i yoxlayırsan, Git qalan hissənin yarısını atır. 64 commit üçün cəmi 6 yoxlama kifayətdir (2⁶ = 64).
```bash
git bisect start
git bisect bad              # indiki vəziyyət — test düşür
git bisect good a1b2c3d     # dünənki commit — test keçirdi
# Git ortadakı commit-ə keçir: testi işə sal və nəticəni bildir
git bisect good             # və ya: git bisect bad
# ... bir neçə dəfə təkrar ...
git bisect reset            # sonda əvvəlki vəziyyətə qayıt
```
Sonda Git “first bad commit” göstərir. Bug report-a həmin commit-in linkini əlavə etmək proqramçının işini xeyli asanlaşdırır.

### Tipik yanlış anlama
“Kodun tarixçəsi tester-ə lazım deyil.” “Nə dəyişdi?” sualı defekt araşdırmasının ən güclü sualıdır, cavabı isə Git tarixçəsindədir.
@nümunə
**Tapşırıq.** `cart.spec.js` testi 1.4.0 relizində keçirdi, indi main-də düşür. Arada 40 commit var. `git bisect` ilə defekti yaradan commit-i tap.
@addımlar
1. **Başlat:** `git bisect start`, sonra `git bisect bad` (main — düşür) və `git bisect good v1.4.0` (reliz teqi — keçirdi).
2. **Yoxlama sayını hesabla:** 40 commit üçün ən çoxu 6 addım lazımdır, çünki 2⁵ = 32 < 40 ≤ 64 = 2⁶.
3. **Hər addımda:** Git ortadakı commit-ə keçir → `npx playwright test tests/cart.spec.js` → nəticəyə görə `git bisect good` və ya `git bisect bad`.
4. **Avtomatlaşdır (istəyə görə):** `git bisect run npx playwright test tests/cart.spec.js` — Git hər addımda testi özü işə salır və nəticəni özü qeyd edir.
5. **Nəticə:** Git “first bad commit” göstərir, məsələn, `e4f5a6b Refactor price formatting`. `git show e4f5a6b` ilə dəyişikliyə bax, `git bisect reset` ilə qayıt və bug report-a commit linkini əlavə et.

### Tez-tez rast gəlinən xətalar
| Xəta | Səbəb | Həll |

### Tipik pipeline
1. **Build:** kod yığılır, paketlər qurulur.
2. **Sürətli yoxlamalar:** linter və unit testlər — bir neçə dəqiqə.
3. **API və inteqrasiya testləri.**
4. **Test və ya staging mühitinə deploy.**
5. **E2E və smoke testlər** — real mühitdə.
6. **Production-a deploy** — avtomatik (Continuous Deployment) və ya təsdiqlə (Continuous Delivery).
Hər mərhələ “keyfiyyət qapısı”dır (quality gate): mərhələ düşərsə, növbətisinə keçid olmur.

### Sürətli rəyin dəyəri
Pipeline 10 dəqiqə çəkirsə, proqramçı hələ mövzunun içindədir və səhvi dərhal düzəldir. 2 saat çəkirsə, o, artıq başqa işə keçib — səhvə qayıtmaq bahadır. Ona görə uzun testlər paralel işə salınır və ya gecə icrasına (nightly) keçirilir.

### Feature flag və geri qaytarma
Bəzi komandalar yeni funksiyanı “bayraq” arxasında canlıya çıxarır: kod production-dadır, amma funksiya yalnız seçilmiş istifadəçilərə açıqdır. Problem olanda bayraq söndürülür. Deploy-dan sonra problem çıxarsa, əvvəlki versiyaya qayıtmaq (rollback) planı da hazır olmalıdır.

GitHub Actions workflow-u `.github/workflows/` qovluğundakı YAML faylıdır: `on` — nə vaxt işə düşür, `runs-on` — hansı maşında, `steps` — ardıcıl addımlar. Playwright testləri hər push və PR-da avtomatik işə düşür, hesabat isə artifact kimi saxlanılır.
@yadda
- YAML-da girinti (boşluqlar) mənalıdır — tab işlətmə.
- `if: always()` — testlər düşsə belə hesabatı saxla.
- Şifrələr faylda yox, `secrets`-də saxlanılır.
@dərin
### Əlavə tətiklər
```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:        # Actions tabında “Run workflow” düyməsi
  schedule:
    - cron: '0 3 * * *'     # hər gün 03:00 UTC (Bakı vaxtı ilə 07:00)
```
`schedule` vaxtı UTC ilə yazılır, Bakı vaxtı isə UTC+4-dür. Planlı icra yalnız əsas budaqdakı workflow faylı ilə işləyir və yüklü saatlarda bir qədər gecikə bilər.

### Şifrələrin istifadəsi
Repo → Settings → Secrets and variables → Actions bölməsində `TEST_PASSWORD` yaradılır, workflow-da isə belə ötürülür:
```yaml
      - name: Testləri işə sal
        run: npx playwright test
        env:
          TEST_PASSWORD: ${{ secrets.TEST_PASSWORD }}
```
Testdə dəyər `process.env.TEST_PASSWORD` ilə oxunur. GitHub loqlarda secret dəyərini `***` ilə gizlədir.

### Brauzerlər üçün matris
```yaml
    strategy:
      fail-fast: false
      matrix:
        project: [chromium, firefox, webkit]
    steps:
      # ... checkout, setup-node, npm ci, brauzerlərin quraşdırılması ...
      - run: npx playwright test --project=${{ matrix.project }}
```
Üç ayrı iş (job) paralel işləyir; `fail-fast: false` biri düşəndə digərlərini dayandırmır.

### Tipik yanlış anlama
“Lokalda keçən test CI-da da keçəcək.” CI maşını fərqlidir: Linux, ekransız (headless) rejim, fərqli vaxt zonası, daha zəif resurslar. CI-da düşən testi oxuyanda mühit fərqlərini də nəzərə al.
@nümunə

@addımlar
1. **Vaxtı çevir:** Bakı vaxtı 08:00 = 04:00 UTC (UTC+4).
2. **Cron yaz:** `on` bölməsinə `schedule:` və altında `- cron: '0 4 * * 1-5'` əlavə et — dəqiqə 0, saat 4, hər gün, hər ay, bazar ertəsi–cümə (1–5).
3. **Secret yarat:** Repo → Settings → Secrets and variables → Actions → New repository secret → ad: `TEST_PASSWORD`, dəyər: şifrə.

### Qırmızı pipeline-ı oxumaq — addım-addım
1. Actions tabında düşən işi (job) aç və qırmızı addımı genişləndir.
2. Test adını, faylı və sətri tap: `tests/cart.spec.js:12`.
3. Xəta mesajını oxu: gözlənilən (Expected) və alınan (Received) dəyərlər.
4. Artifacts bölməsindən HTML hesabatı yüklə və trace-i aç.
5. Son commit-lərə bax: problem hansı dəyişiklikdən sonra başlayıb?

### Təsnifat və addımlar
| Səbəb | Əlamət | Addım |
| --- | --- | --- |
| Məhsul defekti | Lokalda da düşür, UI-də problem görünür | Bug report + CI linki |
| Köhnəlmiş test | Funksiya qəsdən dəyişib (yeni mətn, yeni lokator) | Testi yenilə, PR aç |
| Mühit | Çox test eyni anda düşür, timeout, 502/503 | Mühitin sahibinə xəbər ver, yenidən işə sal |
| Flaky | Yenidən işə salanda keçir | Flaky siyahısına əlavə et, səbəbini araşdır |

Formalar defektlərin ən çox olduğu yerdir: məcburi sahələr, validasiya, xəta mesajları, boşluqlar, kopyala-yapışdır, klaviatura, ikiqat göndərmə, avtodoldurma və “Geri” düyməsi yoxlanılır. Əsas validasiya serverdə olmalıdır.
@yadda
- Client validasiyası rahatlıq üçün, server validasiyası təhlükəsizlik üçündür.
- Xəta mesajı sahənin yanında, aydın və düzələndə yox olmalıdır.
- İkiqat göndərmə dublikat yaratmamalıdır.
@dərin
### Xəta mesajının keyfiyyəti
Yaxşı xəta mesajı: **nə** səhvdir, **necə** düzəltmək olar, **harada** — sahənin yanında. Pis: “Xəta baş verdi”, “Invalid input”, ya da yalnız qırmızı haşiyə. Yoxla: mesaj nə vaxt çıxır — yazarkən, sahədən çıxanda, yoxsa göndərəndə? Tələb bunu deməlidir.

### Data itkisinin qarşısı
Uzun formada bir sahə səhv olduqda qalan məlumat silinməməlidir. Şifrə sahəsi təhlükəsizlik üçün təmizlənə bilər, amma ad, ünvan, telefon qalmalıdır. Səhifəni təsadüfən yeniləmək və ya “Geri” basmaq da böyük formada qaralama itkisinə səbəb olmamalıdır — tələbdə qayda varmı, yoxla.

### Server validasiyasını necə yoxlamaq olar?
Öz test mühitində:
- DevTools → Elements-də `maxlength`, `required`, `pattern` atributunu sil və göndər.
- Network-dan sorğunu “Copy as cURL” edib Postman-da dəyişdirərək göndər (Fəsil 15).
Server yanlış datanı qəbul edirsə, bu, təhlükəsizlik və data keyfiyyəti defektidir.

### Tipik yanlış anlama
“Forma göndərildi — test keçdi.” Göndərilən datanın düzgün saxlandığını (baza, e-poçt, profil) yoxlamadan forma testi yarımçıqdır.
@nümunə
**Tapşırıq.** Çatdırılma ünvanı formasında sahələr: ad, telefon, şəhər (siyahı), küçə, mənzil (məcburi deyil). 6 test ideyası yaz — xəta mesajı, data itkisi və server validasiyası daxil olmaqla.
@addımlar
1. **Məcburi sahələr:** boş göndər — ad, telefon, şəhər və küçə üçün ayrı-ayrı mesajlar; mənzil üçün mesaj yoxdur.
2. **Format:** telefon “050 123 45 67” boşluqlarla yapışdırılır — qəbul olunur və vahid formata salınır.
3. **Data itkisi:** telefonu səhv yaz, göndər — xəta çıxır, amma ad, şəhər və küçə qalır.
4. **Boşluqlar:** adın əvvəlində və sonunda boşluq — saxlananda təmizlənir (trim).
5. **İkiqat göndərmə:** “Yadda saxla” düyməsini tez iki dəfə bas — bir ünvan yaranır.
6. **Server validasiyası:** test mühitində telefon sahəsinin `pattern` atributunu silib hərflərlə göndər — server rədd edir.
@növbən
İş elanına müraciət formasında sahələr: ad, email, telefon, CV faylı, motivasiya məktubu (maks. 1000 simvol). 6 test ideyası yaz — xəta mesajı, data itkisi, sərhəd və server validasiyası daxil olmaqla.

### Naviqasiyanın gizli problemləri
- **Dərin linklər:** sayt daxilindəki səhifənin URL-ini yeni tabda açanda səhifə düzgün yüklənirmi, yoxsa ana səhifəyə atır?
- **Filtrlərin vəziyyəti:** filtr seçib məhsula keç, “Geri” bas — filtrlər qalırmı?
- **Yönləndirmə dövrəsi:** login-dən sonra əvvəlki səhifəyə qayıdırmı, yoxsa həmişə ana səhifəyə?
- **Hash və tablar:** SPA saytlarında “Geri” düyməsi tabları dəyişirmi, yoxsa saytdan çıxarır?

### Linkləri toplu yoxlamaq
Böyük saytda yüzlərlə link var. Alətlər (link checker-lər, Lighthouse-un SEO bölməsi) qırıq linkləri avtomatik tapır. Tester əsas menyuları və kritik yolları əl ilə, qalanını alətlə yoxlayır.

### Səhv səhifələri
- **404:** sayt dizaynında, axtarış və ana səhifə linki ilə.
- **500:** texniki detal göstərmədən, “bir az sonra yenidən cəhd edin” mesajı ilə.
- **Texniki işlər (maintenance):** planlı dayanma zamanı aydın məlumat.

### Tipik yanlış anlama
“Naviqasiya — sadə şeydir, test etməyə dəyməz.” İstifadəçi “Geri” basanda ödəniş formasının ikinci dəfə göndərilməsi kimi ciddi problemlər məhz naviqasiyada çıxır.
@nümunə
**Tapşırıq.** Onlayn mağazada “Kateqoriya → məhsul siyahısı (filtrlərlə) → məhsul səhifəsi → səbət” yolu üçün 5 naviqasiya testi yaz.
@addımlar
1. **Breadcrumbs:** məhsul səhifəsində “Ana səhifə > Elektronika > Telefonlar” görünür və hər link işləyir.
2. **Geri və filtrlər:** “Qiymət 300–500” filtrini seç, məhsula keç, “Geri” bas — filtr və səhifə nömrəsi qalır.
3. **Dərin link:** məhsul səhifəsinin URL-ini yeni tabda aç — eyni məhsul açılır.
4. **Səbətdən geri:** səbətdən “Alış-verişə davam et” — sonuncu baxılan kateqoriyaya qaytarır (tələbə görə).
5. **404:** URL-də məhsul ID-sini mövcud olmayana dəyiş — saytın dizaynında 404 səhifəsi, axtarış sahəsi ilə.
@növbən
Xəbər saytında “ana səhifə → kateqoriya → xəbər → müəllifin digər xəbərləri” yolu üçün 5 naviqasiya testi yaz — “Geri” düyməsi, dərin link və 404 daxil olmaqla.

Hər ekran yalnız “normal” vəziyyətdə deyil:
- **Boş vəziyyət:** səbət boşdur, axtarış nəticə vermədi — nə göstərilir?
- **Yüklənmə:** loader və ya skeleton görünürmü?
- **Xəta:** server cavab vermədi — səliqəli mesaj?
- **Çox data:** 1000 sifarişlik tarixçə — səhifələmə, performans.

### Vizual regression
Avtomatlaşdırmada ekranın şəkli əvvəlki “etalon” şəkillə müqayisə olunur; fərq çıxanda insan baxır: bu, gözlənilən dəyişiklikdir, yoxsa baq? Playwright-da `toHaveScreenshot()` bu işi görür. Bu, kiçik CSS dəyişikliyinin başqa səhifəni pozmasını tutur.

### Piksel dəqiqliyi lazımdırmı?
Maketlə 1–2 piksel fərq çox vaxt baq deyil. Fokus: düzülüşün pozulması, üst-üstə düşmə, kəsilmiş mətn, yanlış rəng (xüsusən statuslar), yanlış şrift ölçüsü. Kiçik fərqləri dizaynerlə razılaşdırılmış qaydaya görə qiymətləndir.

### Brauzer matrisi necə qurulur?
1. Analitikadan brauzer və versiya paylarını götür.
2. Trafikin böyük hissəsini (məsələn, 95%) əhatə edən birləşmələri seç.
3. Kritik ssenariləri (login, ödəniş) hamısında, qalanını əsas brauzerdə test et.

### Tipik cross-browser problemləri
- Tarix və vaxt seçicisinin fərqli görünüşü və davranışı.
- CSS xüsusiyyətlərinin dəstəyindəki fərqlər (yeni xüsusiyyətlər köhnə versiyalarda işləmir).
- Şriftlərin fərqli çəkilməsi, mətnin sətirdən çıxması.
- Fayl yükləmə, kopyala-yapışdır, autofill fərqləri.
- Safari-də üçüncü tərəf cookie-lərin məhdudlaşdırılması.

### Tipik yanlış anlama

CSS-də “media query”lərlə müəyyən enlərdə düzülüş dəyişir (məsələn, 768 px-dən kiçikdə menyu burgerə çevrilir). Defektlər çox vaxt breakpoint-in tam sərhədində olur: 767 və 768 px — BVA burada da işləyir!

- Klaviatura açılanda forma sahəsi və “Göndər” düyməsi görünür qalırmı?

### Toxunma hədəfləri
Kiçik və bir-birinə yaxın linklər səhv basılmaya səbəb olur. WCAG və platforma qaydaları minimum toxunma ölçüsü tövsiyə edir (adətən 44–48 px). Lighthouse bunu “Tap targets” kimi yoxlayır.

2. **767 və 768 px (breakpoint sərhədi):** düzülüş düzgün dəyişir, elementlər “yarımçıq” vəziyyətdə ilişmir.

### POUR prinsipləri
- **Perceivable (qavranıla bilən):** şəkillərin alt mətni, videoların subtitrləri, kontrast.
- **Operable (idarə oluna bilən):** klaviatura, kifayət qədər vaxt, tələ (trap) olmaması.
- **Understandable (anlaşıla bilən):** aydın mətn, gözlənilən davranış, xəta izahı.
- **Robust (möhkəm):** ekran oxuyucu və digər köməkçi texnologiyalarla uyğunluq.

### Klaviatura testinin addımları
1. Siçanı kənara qoy.
2. Tab ilə irəli, Shift + Tab ilə geri get — sıra məntiqlidirmi?
3. Fokus görünürmü (çərçivə, rəng)?
4. Enter və Space düymələri aktivləşdirirmi?
5. Açılan pəncərədən Esc ilə çıxmaq olurmu, fokus “tələyə” düşmürmü?

### Qanunlar
Bir çox ölkədə əlçatanlıq qanuni tələbdir. Məsələn, Avropa İttifaqında Avropa Əlçatanlıq Aktı 2025-ci ilin iyunundan bir çox rəqəmsal xidmətə tətbiq olunur. Beynəlxalq bazara çıxan məhsullar üçün bu, ciddi risk sahəsidir.

### Tipik yanlış anlama
“Lighthouse 100 bal verdi — sayt əlçatandır.” Alətlər kontrast və alt mətnin varlığını yoxlayır, amma alt mətnin mənalı olub-olmamasını və klaviatura axınının məntiqini insan yoxlamalıdır.
@nümunə
**Tapşırıq.** Qeydiyyat forması üçün 6 əlçatanlıq testi yaz.
@addımlar
1. **Klaviatura:** yalnız Tab, Shift + Tab, Enter ilə formanı doldur və göndər.
2. **Fokus:** hər sahədə fokus aydın görünür.
3. **Label:** hər sahənin label-i var; ekran oxuyucu (NVDA) sahəni adı ilə oxuyur, yalnız placeholder yox.
4. **Xəta:** səhv email-də mesaj mətnlə göstərilir və ekran oxuyucu onu oxuyur — yalnız qırmızı haşiyə yox.
5. **Kontrast:** mətn və düymələr 4,5:1 nisbətinə cavab verir (DevTools-da yoxla).
6. **Böyütmə:** 200%-də forma istifadə oluna bilir, mətnlər üst-üstə düşmür.
@növbən
Onlayn bank tətbiqinin “köçürmə” ekranı üçün 6 əlçatanlıq testi yaz: klaviatura, fokus, ekran oxuyucu, xəta mesajı, kontrast və vaxt məhdudiyyəti (sessiya) daxil olmaqla.

### OWASP Top 10 nədir?
OWASP — veb təhlükəsizliyi üzrə açıq icma. Onun “Top 10” siyahısı ən geniş yayılmış risk kateqoriyalarını toplayır. Siyahının başında uzun müddətdir **pozulmuş giriş nəzarəti** (Broken Access Control) dayanır — yəni istifadəçinin icazəsi olmayan şeyə çatması. Tester-in URL-də ID dəyişməsi məhz bu kateqoriyanı yoxlayır.

### Tester səviyyəsində təhlükəsizlik yoxlamaları
- **Rollar matrisi:** hər rol (qonaq, istifadəçi, menecer, admin) hər səhifəni və API-ni çağıranda nə baş verir? Cədvəl kimi yoxla.
- **Data sızması:** API cavabında ekranda göstərilməyən, amma lazımsız həssas sahələr (başqasının telefonu, daxili qeydlər) varmı?
- **Şifrə siyasəti:** zəif şifrələr rədd olunurmu, şifrə URL-də və loglarda görünmürmü?
- **Xəta mesajları:** “bu email qeydiyyatda yoxdur” kimi mesajlar hesabların mövcudluğunu açırmı?
- **Brute force:** çoxsaylı səhv login cəhdi bloklanırmı və ya captcha istənirmi?

### Etik qaydalar
Tapdığın zəifliyi istismar etmə, başqa istifadəçilərin datasına baxmağa davam etmə, sübutu minimal saxla və dərhal məsul şəxsə bildir. Canlı sistemdə və icazəsiz sistemdə heç bir yoxlama aparma.

### Tipik yanlış anlama
“Təhlükəsizlik — yalnız pentester-lərin işidir.” Dərin testi onlar aparır, amma icazə səhvlərinin çoxu adi funksional testdə, düzgün sual verən tester tərəfindən tapılır.
@nümunə
**Tapşırıq.** Onlayn mağazanın test mühitində “Sifarişlərim” funksiyası üçün icazələrlə bağlı 5 yoxlama yaz.

2. **API səviyyəsi:** eyni yoxlamanı API sorğusu ilə et — UI gizlətsə də, API data qaytarmamalıdır.

### Core Web Vitals
Google istifadəçi təcrübəsini üç əsas göstərici ilə ölçür:
- **LCP (Largest Contentful Paint):** əsas məzmunun görünmə vaxtı — yaxşı hesab olunan hədd təxminən 2,5 saniyədir.
- **INP (Interaction to Next Paint):** klikə reaksiyanın sürəti.
- **CLS (Cumulative Layout Shift):** səhifənin “atılması” — oxuyarkən elementlərin yerdəyişməsi.
Lighthouse və PageSpeed Insights bunları göstərir; CLS xüsusilə tester-in gördüyü “düymə qaçdı və səhv yerə basdım” problemidir.

### Manual tester üçün sadə performans müşahidələri
- Eyni əməliyyat müxtəlif vaxtlarda nə qədər çəkir?
- Hansı sorğu ən uzun çəkir (Network → Time)?
- Səhifədə neçə sorğu var, eyni sorğu təkrar gedirmi?
- Siyahı uzandıqca (100, 1000 element) sürət necə dəyişir?

### Nəticəni necə yazmalı?
“Yavaşdır” yox: “Kataloq səhifəsi Slow 4G-də 9,8 saniyəyə açılır (Lighthouse LCP 7,1 san); ən ağır fayl — 3,2 MB-lıq banner şəkli.” Rəqəm və mühit həmişə göstərilir.

### Tipik yanlış anlama
“Mənim sürətli internetimdə tez açılır — problem yoxdur.” İstifadəçilərin çoxu mobil şəbəkədədir; throttling ilə yoxlamadan performans haqqında nəticə çıxarma.
@nümunə
**Tapşırıq.** Ana səhifənin performansı haqqında şikayətlər var. 5 addımlıq yoxlama planı yaz və nəticəni necə qeyd edəcəyini göstər.
@addımlar
1. **Mühit:** gizli pəncərə, Network → “Disable cache”, throttling “Slow 4G”.
2. **Ölçmə:** səhifəni 3 dəfə yüklə, “Load” vaxtını qeyd et — orta və ən pis nəticə.
3. **Ən ağır fayllar:** Size-a görə sırala — 1 MB-dan böyük şəkillər, böyük JS faylları.
4. **Lighthouse:** Performance balı, LCP, CLS — ekran şəkli ilə.
5. **Qeyd:** “Ana səhifə Slow 4G-də orta 8,4 san (3 ölçmə); LCP 6,2 san; 2,8 MB-lıq hero şəkli; CLS 0,25 — banner gec yüklənəndə məzmun aşağı sürüşür.”
@növbən
Məhsul axtarışı nəticələr səhifəsinin performansını yoxlamaq üçün 5 addımlıq plan yaz və nəticəni rəqəmlərlə necə təqdim edəcəyini bir nümunə cümlə ilə göstər.

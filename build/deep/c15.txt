### API növləri
- **REST** — ən geniş yayılmış: resurslar, URL-lər, HTTP metodları, adətən JSON.
- **SOAP** — köhnə, ciddi formatlı, XML əsaslı; banklarda və dövlət sistemlərində hələ də rast gəlinir.
- **GraphQL** — bir endpoint, client lazım olan sahələri sorğuda özü seçir.
- **gRPC** — servislər arası sürətli əlaqə, ikilik formatla.
Junior tester üçün REST və JSON əsasdır; digərlərinin varlığını bilmək kifayətdir.

### API sənədi necə oxunur?
Swagger (OpenAPI) səhifəsində hər endpoint üçün: metod və yol, parametrlər (məcburi/məcburi olmayan, tip), sorğu gövdəsinin nümunəsi, mümkün cavab kodları və nümunə cavablar. Tester bunları tələb kimi oxuyur: “422 cavabı sənəddə var — hansı halda qayıdır?” Çox vaxt “Try it out” düyməsi ilə birbaşa sorğu göndərmək də olur.

### API-nin “müqaviləsi”
API sənədi client ilə server arasında müqavilədir. Sahənin adı, tipi və ya məcburiliyi xəbərsiz dəyişəndə mobil tətbiq sına bilər — buna “breaking change” deyilir. Tester sənədlə faktiki cavabı müqayisə edərək bunu tutur.

### Tipik yanlış anlama
“API testi yalnız avtomatlaşdırma mütəxəssislərinin işidir.” Postman ilə API testi manual tester üçün ən sürətli və ən faydalı bacarıqlardandır.

@addımlar

2. **Tapılmayan şəhər:** `city=Abcdef` → 404 və aydın xəta mesajı.

### Yaxşı REST dizaynının əlamətləri
- Resurslar isimdir və çoxluqdadır: `/users`, `/orders` (fel yox: `/getUsers` deyil).
- İç-içə resurslar: `/users/5/orders` — 5 nömrəli istifadəçinin sifarişləri.
- Filtr və səhifələmə parametrlərlə: `/orders?status=paid&page=2&limit=20`.
- Statelessness: hər sorğu özündə lazım olan hər şeyi daşıyır (məsələn, token).
Tester bu qaydaları yoxlamır, amma uyğunsuzluqları müşahidə edə bilər: eyni API-də bir yerdə `userId`, digərində `user_id`.

### JSON-un sərt qaydaları
- Açarlar həmişə cüt dırnaqda: `"name"`.
- Sonuncu elementdən sonra vergül olmaz.
- Şərh (comment) yazmaq olmaz.
- Kəsr nöqtə ilə: `125.50`, vergül ilə yox.
Postman-da səhv JSON göndəriləndə server 400 qaytarmalıdır — bu, ayrıca test ideyasıdır.

### Cavab quruluşunun yoxlanması
- Bütün gözlənilən sahələr var?
- Tiplər düzgündür (id — number, email — string, roles — array)?
- `null` gözlənilən yerdədir, yoxsa sahə ümumiyyətlə yoxa çıxır?
- Pul məbləğləri necə qaytarılır — 125.5, “125.50”, yoxsa qəpiklə 12550?

### Tipik yanlış anlama
“Cavab gəldisə, quruluş düzgündür.” Sahənin tipinin dəyişməsi (ədəddən mətnə) mobil tətbiqi çökdürə bilər — quruluşun yoxlanması API testinin vacib hissəsidir.
@nümunə
**Tapşırıq.** Cavab: `{"id": "17", "name": "Leyla", "isActive": "true", "balance": 125.5, "phone": null, "roles": "customer"}`. Sənəddə id — number, isActive — boolean, roles — array yazılıb. Uyğunsuzluqları tap.
@addımlar
1. **id:** `"17"` mətndir, sənəddə number — tip uyğunsuzluğu.
2. **isActive:** `"true"` mətndir, boolean deyil — `if (isActive)` yoxlaması “false” mətnini də doğru sayar!
3. **roles:** `"customer"` mətndir, array olmalı idi: `["customer"]`.
4. **phone: null:** sənədə uyğundur (telefon yoxdur) — problem deyil, amma UI-nin null-u necə göstərdiyini yoxla.
5. **Nəticə:** 3 müqavilə pozuntusu — bir bug report-da cədvəl kimi yaz və ya hər birini ayrıca aç (komanda qaydasına görə).
@növbən
Cavab: `{"orderId": 9001, "total": "39,80", "items": {"name": "Termos"}, "paid": 1, "createdAt": "24/10/2026"}`. Sənəd: total — number, items — array, paid — boolean, createdAt — ISO format (YYYY-MM-DD). Uyğunsuzluqları tap və hər birinin mümkün təsirini yaz.

### Kolleksiyanı necə təşkil etməli?
Qovluqlar resurslara görə: Users, Posts, Comments. Hər qovluqda əvvəl pozitiv, sonra neqativ sorğular. Sorğuların adı nəyi yoxladığını deyir: “GET user — mövcud ID (200)”, “GET user — mövcud olmayan ID (404)”. Belə kolleksiya həm test dəsti, həm də canlı sənəddir.

### Dəyişən səviyyələri (scopes)
Postman-da dəyişənlər bir neçə səviyyədə olur: global, collection, environment, data (Runner faylından) və local (skript daxilində). Eyni adlı dəyişən bir neçə yerdədirsə, daha dar səviyyə qalib gəlir (local → data → environment → collection → global). Qarışıqlıq olmasın deyə: server ünvanları — environment-də, kolleksiyaya aid sabitlər — collection-da.

### Kolleksiyanı paylaşmaq
Kolleksiyanı JSON kimi ixrac edib GitHub-a qoymaq olar (portfolio üçün əla). Token və şifrələr environment-də saxlanılır və environment faylı ayrıca, ehtiyatla paylaşılır — ya da “secret” tipli dəyişən kimi işarələnir.

### Tipik yanlış anlama
“Postman yalnız sorğu göndərmək üçündür.” Postman-da avtomatik yoxlamalar, data-driven icra, mock serverlər və sənədləşmə də var — manual tester üçün tam test aləti ola bilər.

2. **Qovluq “Users”:** “GET users — siyahı (200)”, “GET user — 1 (200)”, “GET user — 9999 (404)”.

### Faydalı yoxlama nümunələri
```javascript
const data = pm.response.json();

pm.test("Cavab massivdir və 10 elementdir", function () {
  pm.expect(data).to.be.an("array");
  pm.expect(data).to.have.lengthOf(10);
});

pm.test("Hər postun userId-si 1-dir", function () {
  data.forEach(function (post) {
    pm.expect(post.userId).to.eql(1);
  });
});

pm.test("Content-Type JSON-dur", function () {
  pm.response.to.have.header("Content-Type");
  pm.expect(pm.response.headers.get("Content-Type")).to.include("application/json");
});
```

### JSON Schema ilə quruluş yoxlaması
Hər sahəni ayrıca yoxlamaq əvəzinə cavabın “şablonunu” (schema) təsvir etmək olar: hansı sahələr məcburidir və tipi nədir. Postman-da `pm.response.to.have.jsonSchema(schema)` bütün quruluşu bir dəfəyə yoxlayır — sahə yoxa çıxanda və ya tip dəyişəndə dərhal düşür.

### Sorğu zənciri (chaining)
Real ssenari bir neçə sorğudan ibarətdir: login → token → istifadəçi yarat → id → istifadəçini yenilə → sil. Hər addım əvvəlkinin nəticəsindən istifadə edir:
```javascript
// Login sorğusunun Post-response hissəsində

pm.environment.set("token", data.token);
```
Növbəti sorğunun Authorization tabında: Bearer Token → `{{token}}`.

### Environment-lərin dəyişdirilməsi
“Test” və “Staging” environment-lərində eyni dəyişən adları (`baseUrl`, `token`) fərqli dəyərlərlə saxlanır. Sağ yuxarıdakı seçimlə mühiti dəyişmək kifayətdir — sorğulara toxunmadan.

### Səhifələmənin (pagination) yoxlanması
- `page=1` və son səhifə — sərhədlər.
- `limit=0`, `limit=-1`, çox böyük `limit` — server limiti tətbiq edirmi?
- Səhifələr arasında element təkrarlanırmı və ya itirmi (xüsusən data dəyişərkən)?
- Cavabda ümumi say (`total`) və növbəti səhifə linki düzgündürmü?

### İdempotency açarı
Ödəniş API-ləri tez-tez xüsusi başlıq qəbul edir (məsələn, `Idempotency-Key`): eyni açarla təkrar POST ikinci ödəniş yaratmır, ilkin nəticəni qaytarır. Tester eyni açarla iki sorğu göndərib bunu yoxlayır.

### Rate limiting
Dəqiqədə icazə veriləndən çox sorğu göndəriləndə 429 qayıtmalıdır və cavabda nə vaxt yenidən cəhd etmək olacağı (`Retry-After`) göstərilə bilər. Bu, test mühitində, icazə ilə yoxlanır.

### Mesajların keyfiyyəti
Xəta cavabında: aydın mesaj, hansı sahənin problemli olduğu, standart format. Mesajda texniki detal (stack trace, SQL sorğusu) olmamalıdır — bu, həm istifadəçi təcrübəsi, həm də təhlükəsizlik məsələsidir.
